# Phase 12 — Testing, Security, Performance

## Method note

The `security-review` skill's git-diff mechanism (`git log origin/HEAD...`) doesn't fit this repo's history — there's a single branch with no separate base/main to diff against, since the whole project was built sequentially on `claude/work-session-lq1l7o` from an empty repo. Rather than force-fit the skill, this phase is a manual review against the master spec's own Phase 12 checklist (XSS, CSRF, SQL injection, auth, rate limiting, prompt injection, data leakage, entitlement enforcement) plus a dependency audit and a local performance smoke test — informed by having written every line of the codebase under review this session.

## Security findings and fixes

| Area | Finding | Action |
|---|---|---|
| Rate limiting | **No rate limiting existed anywhere** — `/api/auth/register`, the credentials login callback, `/api/ai/chat`, `/api/ai/explain`, and `/api/billing/checkout` were all uncapped. | Added `lib/rateLimit.ts` (in-memory fixed-window limiter, documented as single-process — see Known Simplifications) and applied it to all five: register (5/15min/IP), login (10/15min/IP), AI chat (20/min/IP — this endpoint is intentionally reachable anonymously, so there's no per-user entitlement to fall back on), AI explain (30/min/IP, since `force=true` bypasses the significant-change cache), billing checkout (10/min/user). Verified live: hit each limit and confirmed a `429` with `Retry-After` at exactly the configured threshold. |
| Security headers | No headers configured at all. | Added `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` restricting camera/mic/geolocation, via `next.config.ts` `headers()`. Verified live via `curl -D -`. A stricter Content-Security-Policy is deferred (noted in the code) rather than shipped half-tested — Next dev mode and the inline JSON-LD `<script>` tags need care to not silently break under a naive CSP. |
| SQL injection | Every database access goes through Prisma's parameterized query builder — no raw SQL anywhere in the codebase (confirmed by grep). | No action needed; safe by construction. |
| XSS | Only one `dangerouslySetInnerHTML` in the whole codebase (`components/seo/JsonLd.tsx`), and it only ever serializes code-authored, static page metadata — never user input. Chat messages and all other user-influenced or AI-influenced text render through normal React children (auto-escaped). | No action needed. |
| CSRF | Auth.js's own endpoints have built-in CSRF token handling. Custom API routes (watchlist, alerts, billing) rely on `SameSite=Lax` session cookies plus requiring `Content-Type: application/json` — a cross-site form POST can't set that header, and a cross-site `fetch` can't attach the session cookie under `SameSite=Lax`. | Accepted as adequate for this stage; documented rather than adding token-based CSRF protection preemptively (would be revisited if the app needs `SameSite=None` for any reason, e.g. embedding). |
| Authorization / IDOR | Checked every mutating route: watchlist item delete, alert PATCH/DELETE, and billing routes all verify the resource belongs to `requireUser()`'s own id before acting. | No gaps found. |
| Secrets in source | Grepped for common secret patterns (`sk_live`, `sk_test_<long>`, AWS key patterns, hardcoded passwords) across the codebase. | None found. All real secrets (`AUTH_SECRET`, `DATABASE_URL`) live in `.env.local`, confirmed gitignored throughout every phase. |
| Prompt injection | Already addressed and tested in Phase 7 (`packages/ai`) — re-verified here that nothing since then reintroduced a path for user input to reach `TRUSTED_MARKET_DATA`. | No new findings. |
| Entitlement enforcement | Re-verified (from Phase 8/11's live tests) that limits are checked server-side on every create, never trusted from client state. | No gaps found. |
| Account enumeration | `/api/auth/register` returns a distinct "already exists" message, which lets an attacker probe which emails have accounts. | Accepted tradeoff, documented rather than silently left unmentioned: fixing this properly needs an email-verification flow (send a link either way, don't reveal registration state), which needs real email-sending infrastructure this environment doesn't have. Rate limiting on the endpoint (see above) at least bounds enumeration speed. |
| Dependency vulnerabilities | `pnpm audit --audit-level=high` found 11 advisories (1 critical, 3 high, 7 moderate). | The critical one (`vitest` <3.2.6, arbitrary file read/execute — only reachable via `vitest --ui`, which this project never runs) was fixed for real by upgrading `vitest` to `^3.2.7` across every package (`apps/web` and all six `packages/*`) — confirmed all 127 tests still pass. The remaining high/moderate findings are `postcss`/`vite` versions bundled *inside* `next`'s and `next-auth`'s own dependency trees (not something this project can `pnpm add` its way out of without an override that risks breaking Next's internal tooling) and affect build-time/dev-server file handling, not the deployed app's runtime attack surface. Documented here rather than silently left out of the report; revisit when Next.js bumps its bundled `postcss`. |

## Testing

- `apps/web` had a placeholder `"no unit tests yet"` test script since Phase 4 — this phase gives it a real Vitest setup (`vitest.config.ts`) and adds tests for the two most important pure-logic modules added since: `lib/rateLimit.ts` (4 tests, including a fake-timers window-reset test) and `lib/validateAlertInput.ts` (7 tests covering all 8 alert types' differing required-field rules, which had been untested since Phase 8).
- Total workspace test count: **127**, up from 116 before this phase, across `@ltp/core` (64), `@ltp/ai` (32), `@ltp/market-data` (11), `@ltp/billing` (5), `@ltp/entitlements` (4), `apps/web` (11).
- Full `pnpm -r test`, `pnpm -r typecheck`, `pnpm --filter=web lint`, and `pnpm --filter=web build` all pass clean.

## Performance

The master spec calls for progressive load testing at 100 / 1,000 / 10,000 / 100,000 concurrent users. **That requires a real staging deployment** — a dev-mode Next.js server on a single sandboxed container with a handful of CPU cores cannot produce a meaningful number at those scales, and pretending otherwise would be fabricating a result. What this phase actually did, honestly:

- Baseline: a single request to `/api/option-chain` (full computed-chain pipeline: MockProvider → validation → `@ltp/core` calculations) took **~0.28s** in dev mode (unoptimized, no production build).
- 10 concurrent requests (bounded via `xargs -P 10`, each with `--max-time`): all succeeded, **~0.55s average** — roughly double the single-request time, consistent with a single Node process doing synchronous CPU-bound work per request without a worker pool.
- 25 concurrent requests: all succeeded, no failures, **~1.06s average**, total wall time ~1.16s.
- **An earlier, more informative incident**: firing 50 raw background `curl` processes at once via a bash `for` loop (not the bounded `xargs -P` approach used for the 10/25 tests) caused severe resource contention — the sandbox's shell became unresponsive to even trivial commands (`echo`, `ls`) for several minutes. On investigation, this looks like it was compounded by spawning 50 OS-level `curl` processes simultaneously in a CPU-constrained container, not purely a Next.js server failure — the 10 and 25-request bounded tests run immediately after recovery, against the same still-running dev server, both succeeded cleanly. This is reported as-is rather than smoothed over: it's a real signal that **this sandbox's resource ceiling, and/or this architecture's single-process synchronous computation, is a genuine constraint worth taking seriously before assuming the current setup scales**, even though the specific test that triggered it wasn't a clean methodology.

**What this means for production readiness**: the Phase 1 architecture's plan — a separate `apps/realtime-gateway` process doing the actual market-data computation, with `apps/web` reading precomputed state from Redis rather than recomputing a full option chain synchronously on every HTTP request — is not just a nice-to-have, it is the specific fix for the latency-growth pattern observed here. This phase did not build that (it would be premature infrastructure without a real provider and real traffic to size it against, per the project's own "avoid speculative infrastructure" rule), but it now has an actual local measurement backing up why it's needed, not just an architectural guess.

## Known simplifications / what still needs real infrastructure

- Real load testing at spec-required scale (100 → 100,000 concurrent users) needs a real staging deployment with real infrastructure sizing — not achievable in a single sandboxed dev container, and not faked here.
- The rate limiter is in-memory/single-process — the same documented limitation as `historicalCollector.ts`, `aiCache.ts`, and `alertEvaluator.ts` from earlier phases (a Phase 13 deployment decision to move to Redis on a multi-instance deployment, not re-derived here).
- No penetration test, dependency SCA tooling beyond `pnpm audit`, or fuzz testing was run — those are typically separate engagements/tools even in a mature engineering org, not something to simulate.
- CSP was deliberately not shipped this phase (see table above) rather than shipped untested.
